# Instrukcja wdrożenia backendu Odwołania2JSON

Pracujesz na `feat/core-engine` w dwuosobowym zespole. Dostarcz przetwarzanie spraw KIO przez CLI i HTTP z jednym system promptem i jednym żądaniem LLM na czytelny PDF. Edytuj `main.py`, `src/kio_extract/`, `prompts/`, `configs/`, `schemas/`, testy Pythona, ewaluację i uruchomienie backendu. Frontend ma własny zakres. Zmiany interfejsu uzgadniaj z jego właścicielem. Przed edycją sprawdź `git status --short --branch` i zachowaj istniejące zmiany w katalogu roboczym. [Podział pracy](../WORK_SPLIT_2.md) · [Kontrakt](../INTERFACES.md) · [Harmonogram](../INTEGRATION_PLAN.md) · [Tablica](../WORKBOARD.md) · [Pytania otwarte](../OPEN_QUESTIONS.md)

## Kolejność prac i decyzje o modelu

| Zadanie | Termin | Wynik do przekazania |
| --- | --- | --- |
| BE01 · Wspólny procesor i regresja CLI | Przed BE02 | Jedna funkcja przetwarzania i walidacji dla obu wejść. |
| BE02 · HTTP i atrapa LLM | Do 6 h | Endpoint i polecenie pozwalające frontendowi samodzielnie uruchomić próbę. |
| BE03 · Adapter Sonnet i kwalifikacja dostawcy konkursowego | Do 11 h | Próba syntetyczna na wybranym modelu oraz zweryfikowana konfiguracja konkursowa albo udokumentowany brak dostępu. |
| BE04 · Ewaluacja i prompt | Pomiar bazowy do 11 h, poprawki do 16 h | Manifest spraw, raport F1 i regresje dla trzech klas. |
| BE05 · OCR CPU | Implementacja do 16 h, odbiór do 19 h | Skan i mieszany PDF przechodzą tym samym procesorem. |
| BE06 · Uruchomienie i demo | Instrukcja do 19 h, próba do 22 h | Powtarzalny start CLI i API, Compose i końcowy raport. |

- **Limit wskazany przez właściciela.** W ścieżce Claude maksymalną klasą jest Sonnet. Użyj jawnie skonfigurowanego, dostępnego identyfikatora Sonnet. Haiku jest dopuszczalną, lżejszą opcją po jawnym wyborze. Model jest wybierany w konfiguracji i pozostaje stały w całym przebiegu. Konfiguracji z Opusem lub wariantem spoza uzgodnionej listy backend odmawia przed pierwszym żądaniem. Nie dobieraj dostawcy na podstawie prefiksu klucza.
- **Próba deweloperska.** Claude Sonnet to model udostępniany na warunkach Anthropic, bez potwierdzonej otwartej licencji modelu. Używaj go do zatwierdzonych prób na syntetycznych danych. Pierwszostronna Claude API oferuje ustawienie inferencji `us` albo `global`, więc sama konfiguracja tej usługi nie potwierdza inferencji ograniczonej do UE/EOG. [Informacje o dostępie do modeli Claude](https://www.anthropic.com/transparency) · [Rezydencja danych Claude API](https://platform.claude.com/docs/en/manage-claude/data-residency)
- **Profil konkursowy.** Według FAQ przekazanego przez użytkownika model open source musi umożliwiać lokalną instalację i używanie bez ograniczeń oraz opłat licencyjnych. Usługodawca API i serwery mają znajdować się w UE. Organizator wymaga przekazania klucza do testów. Potwierdź licencję, usługodawcę i region docelowego modelu. Haiku i Sonnet służą do wcześniejszych pomiarów rozwojowych. [Warunki techniczne i środowisko UZP](https://raw.githubusercontent.com/Urzad-Zamowien-Publicznych/hacknation-2026/main/README.md)
- **Sekret.** Odczytuj `LLM_API_KEY` wyłącznie ze środowiska procesu. Jawne są `LLM_PROVIDER`, `LLM_BASE_URL` i `LLM_MODEL`. Do przykładów wpisuj wyłącznie wartości przykładowe. Ustawienie klucza przez użytkownika nie określa protokołu, endpointu ani modelu. Przed próbą sieciową potwierdź, że ustawiono właściwą parę dostawca–adres dla tego klucza. Zachowaj niezależne konfiguracje prób syntetycznych i konkursowych.

## BE01 · Wydzielenie wspólnego procesora

**Punkt startu.** Status BE01 `DONE` na tablicy obejmuje istniejący fundament. Wydzielenie procesora to pierwszy krok BE02. [CLI](../../src/kio_extract/cli.py) buduje konfigurację, wybiera tryb, czyta PDF i waliduje payload w pętli plików. [PromptExtractor](../../src/kio_extract/prompt_extraction.py) przygotowuje kopertę `typ`/`dane` i ją sprawdza. [Czytnik PDF](../../src/kio_extract/pdf_reader.py) przyjmuje już opcjonalny OCR. Bazowy zestaw miał 9 przechodzących testów na Pythonie 3.13.16 przy przygotowaniu instrukcji. Uruchom go ponownie przed refaktoryzacją.

**Pliki.** Dodaj `src/kio_extract/processing.py`. Dostosuj `cli.py` i istniejące testy. Jeśli potrzebujesz testów procesora niezależnie od wejść, dodaj `tests/test_processing.py`. Korzystaj z `contracts.py`, `load_configs`, `PromptExtractor`, `classify` i `resolve_extractor`.

1. Zbuduj procesor raz z plików konfiguracji, walidatorów `Draft202012Validator` i wybranej strategii. Wstrzykuj opcjonalny `LLMClient` i `OCR` przy tworzeniu. Minimalny interfejs roboczy to `process(path: Path) -> tuple[ClassificationResult, JsonObject | None]`. Dla błędu PDF, OCR, modelu lub walidacji zgłasza istniejący `DocumentError` z kodem.
2. Wywołaj `extract_pdf(path, ocr=...)`. Strony wymagające OCR mają zostać obsłużone przed modelem. Jeśli nie da się ich odczytać, zwróć błąd dokumentu. Rozpoznany negatyw przechodzi jako `ClassificationResult("unknown", ...)` i `None`. W trybie z LLM klasyfikacja i ekstrakcja dzieją się w jednej odpowiedzi. W trybie regułowym zachowaj dotychczasową klasyfikację i konfigurację ekstraktorów.
3. Po dekodowaniu koperty użyj walidatora właściwej klasy z `FORMAT_CHECKER`. Przekaż wyłącznie `data`, gdy jest zgodne ze schematem. Odrzuć niepoprawne daty, dodatkowe pola i liczby nienadające się do poprawnego zapisu JSON. Nie przepisuj wadliwych typów na domyślne wartości. W błędzie nie umieszczaj wartości wyciągniętych z PDF-u.
4. CLI zachowuje `--llm`, `--prompt`, `--configs`, `--schemas`, `--input`, `--output` i oba tryby wyniku negatywnego. Pętla CLI wybiera ścieżki, wywołuje procesor, zapisuje atomowo wynik oraz raportuje błędy. Zakończ kodem 0 przy pełnym powodzeniu, 1 przy błędzie pliku i 2 przy błędzie konfiguracji. Uruchomienia porównawcze wykonuj na świeżym `output/`.

**Odbiór.** Wszystkie dotychczasowe testy przechodzą. Przetwarzanie poprawnego PDF-u zużywa jedno wywołanie atrapy, a uszkodzony, zaszyfrowany lub nieczytelny PDF zostaje odrzucony przed wywołaniem dostawcy. Odpowiedzi trzech klas przechodzą walidację, a niepoprawny payload zwraca `invalid_output`.

## BE02 · Endpoint dla frontendu

**Pliki.** Dodaj `src/kio_extract/api.py`, `tests/test_api.py` i zależności `fastapi`, `python-multipart`, `uvicorn`. Testy aplikacji wymagają `httpx` w `requirements-dev.txt`. Po zweryfikowaniu instalacji na Pythonie 3.13 przypnij sprawdzone wersje.

1. Udostępnij fabrykę `create_app` z możliwością podstawienia procesora w testach. W trybie normalnym utwórz procesor przez tę samą konfigurację co CLI. Moduł API ma obsługiwać HTTP, a nie implementować odrębnej ekstrakcji. Jako punkt startowy użyj synchronicznej obsługi PDF i LLM, bez blokowania pętli asynchronicznej serwera. [Obsługa wielu plików w FastAPI](https://fastapi.tiangolo.com/tutorial/request-files/#multiple-file-uploads)
2. `POST /api/extract` odczytuje wielokrotne pola `files`. Przetwarzaj kolejno. Tymczasowe ścieżki generuje serwer i sprząta po każdym pliku lub po całym żądaniu, również po wyjątku. Do odpowiedzi przekaż nazwę bez komponentów ścieżki Windows i POSIX. Używaj listy wyników w kolejności multipart, także dla zduplikowanych nazw. Kopiuj zawartość porcjami. Ustal z frontendem komunikat i sposób obsługi limitów po pomiarze przykładowych spraw.
3. Zastosuj dokładną kopertę i statusy z [kontraktu](../INTERFACES.md#api-dla-frontendu) oraz [fixture](../fixtures/extract-response.json). `error` dostaje kod i bezpieczny komunikat. `ok` i `unknown` mają kształt jak w próbce. Przerwij obsługę całego żądania przy wadliwym formularzu i mapuj ten przypadek na uzgodniony HTTP 400 także wtedy, gdy framework standardowo zwróciłby 422. `DocumentError` z pojedynczego dokumentu daje wpis `error` przy HTTP 200. Nie ujawniaj śladu wyjątku, ścieżki tymczasowej ani treści odpowiedzi dostawcy.
4. Przygotuj lokalny, deterministyczny dostawca testowy, najlepiej uruchamiany osobno jako `tests/support/fake_llm_server.py` na pętli zwrotnej. Odpowiedź ustalaj z treści syntetycznej próbki, więc zmiana nazwy PDF-u nie zmienia wyniku. Przekaż frontendowi polecenie startu, bazowy URL API, próbki PDF oraz oczekiwaną odpowiedź. Na etapie P0 frontend może użyć proxy deweloperskiego do `/api`. Jeśli wybierzecie oddzielne originy, uzgodnij dokładny origin do lokalnej konfiguracji.

**Odbiór.** Testowe żądanie zawiera działający PDF, uszkodzony plik i negatyw w tej kolejności. Odpowiedź daje `ok`, `error`, `unknown` oraz zachowuje nazwy. Osobno przetestuj dwie takie same nazwy, pusty formularz, trzy poprawne klasy, `invalid_output` i błąd LLM. Porównaj `data` z plikiem zapisanym przez CLI dla tego samego PDF-u na tej samej atrapie. Frontend potwierdza rzeczywiste wywołanie lokalnego endpointu.

## BE03 · Adapter modelu i test dostawcy

**Pliki.** Zachowaj `src/kio_extract/providers/chat.py` dla istniejących endpointów. Jeśli klucz jest z natywnej Claude API, dodaj `src/kio_extract/providers/anthropic.py`, wspólny wybór klienta z konfiguracji i `tests/test_llm_providers.py`. `LLM_PROVIDER=chat` zachowuje dotychczasowy protokół i jest domyślne dla kompatybilności. `LLM_PROVIDER=anthropic` wybiera Claude Messages. Jeśli klucz jest z bramy lub chmury pośredniczącej, zacznij od jej udokumentowanych adresu, protokołu i uwierzytelnienia. Ustal jawnie właściwy zestaw `LLM_PROVIDER`, `LLM_BASE_URL` i `LLM_MODEL` przed włączeniem trybu LLM.

1. Zachowaj `LLMClient.extract_json(*, instructions, text, schema)`. Dla natywnego Claude wysyłaj `POST /v1/messages`, nagłówki `x-api-key`, `anthropic-version`, `Content-Type`, jawny `model` i `max_tokens`. Wybierz udokumentowaną wersję API i testuj dokładny URL bez podwójnego `/v1`. `instructions` oraz opis koperty trafiają do `system`, JSON stron do jednej wiadomości `user`. Ustal limit odpowiedzi przed próbą, np. startowo 4096 tokenów, i potwierdź go na najdłuższej syntetycznej próbce. Zachowaj timeout klienta. Jedna próba dokumentu oznacza jedno żądanie, dlatego nie włączaj automatycznych ponowień ani drugiego wywołania naprawiającego format. [Claude Messages API](https://platform.claude.com/docs/en/api/http/messages)
2. Obecny `ChatClient` wysyła `response_format: json_object` i `temperature: 0`. Warstwa zgodności Claude odrzuca `json_object`, a dla nowszych modeli narzuca też ograniczenia parametru `temperature`. Natywny adapter w P0 wymusza JSON instrukcją i waliduje go lokalnie. Opcjonalny `output_config.format` można dodać po potwierdzeniu zgodności schematu. Bieżąca koperta ma `if`/`then`/`else`, a `dane` ma zależny kształt. Przed użyciem trybu strukturalnego przygotuj i przetestuj osobny schemat transportowy. Jednym wariantem jest `anyOf` z osobną gałęzią dla każdej klasy i `unknown`, z pełnymi polami obiektów. Zachowaj kanoniczny schemat UZP i jego pełną walidację w aplikacji. [Zgodność Claude z OpenAI SDK](https://platform.claude.com/docs/en/cli-sdks-libraries/libraries/openai-sdk) · [Structured outputs i ograniczenia](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#json-schema-limitations)
3. Dekoduj tekstowe bloki odpowiedzi po poprawnym zakończeniu. Odmowa, ucięcie limitu, brak tekstu, HTTP inne niż 200 i wadliwy JSON dają udokumentowane kody `DocumentError`. Wykorzystaj istniejące `llm_http`, `llm_connect`, `llm_incomplete` i `llm_json`, o ile pasują do sytuacji. Kopertę i payload klasy nadal sprawdzają wspólne walidatory. W logu podawaj kod, czas i ewentualne liczniki tokenów. Pomijaj nagłówki, dokument, treść odpowiedzi modelu i sekret.
4. Przygotuj testy adaptera na zastąpionym transporcie. Sprawdź nagłówki, przekazywanie system/user, blokadę Opusa jeszcze przed transportem, obsługę limitu i złą odpowiedź. Dopiero po potwierdzeniu jawnej konfiguracji wykonaj kontrolowaną próbę na syntetycznym PDF-ie. W raporcie zapisz identyfikator modelu, endpoint bez danych uwierzytelniających, datę, rodzaj danych i wynik. Próba Sonnet potwierdza integrację techniczną. Wynik konkursowy wymaga osobnej próby na kwalifikowanej konfiguracji.

**Odbiór.** Testy lokalne działają bez klucza. Przy skonfigurowanym dostępie czytelny PDF daje dokładnie jedno żądanie i lokalnie zwalidowane dane. Profil konkursowy ma udokumentowaną licencję, lokalizację firmy i obsługi żądań oraz przebieg na jednej rzeczywistej sprawie. Jeżeli profil jest niedostępny, podaj brakujący warunek jako blokadę tej próby.

## BE04 · Lokalny evaluator i poprawki prompta

**Pliki.** Dodaj `evaluation/evaluate.py`, jawny manifest podziału spraw w `evaluation/`, `tests/test_evaluation.py` i regresje w `tests/fixtures/`. Porównania LLM zapisuj w `artifacts/`. Strojenie dotyczy `prompts/system_pl.md` i `options.llm_instructions` danej klasy. Schemat aktualizuj tylko po potwierdzeniu kontraktu.

1. Ustal klucz porównania `identyfikator sprawy + względna nazwa wejściowa`. Zapisz jawne odwzorowanie `potwierdzenie_przelewu.pdf` → `przelew.json`. Rozdziel całe sprawy na rozwój, walidację i próbę końcową. Kopie negatywów grupuj po skrócie zawartości. Zachowaj manifest od pierwszego pomiaru. Zestaw końcowy pozostaw na zamknięcie prac.
2. Czytaj poprawne wyniki według klas. Traktuj pusty plik lub `{}` jako przewidzianą reprezentację `unknown`. Brak pliku, niezgodny schemat i nieprawidłowy JSON ewidencjonuj jako błędy. Oczekiwane wartości brakującego dokumentu wlicz do FN. W macierzy klasyfikacji pokaż wszystkie trzy klasy, `unknown` i błędy techniczne. Nie zaliczaj błędu odczytu jako trafienia negatywu.
3. Porównuj typowane wartości według ścieżek. `null`, puste napisy i puste listy oznaczają brak obserwacji w lokalnej metodzie. Zachowuj różnicę pomiędzy napisem i liczbą, w tym wiodące zera identyfikatorów. W listach łącz rekordy po jednoznacznym identyfikatorze, a potem po jednoznacznej nazwie. Przy braku dopasowania zastosuj udokumentowaną regułę i pokazuj taki przypadek w raporcie. Nie scalaj pełnomocnika z podpisującym ani rachunku nadawcy z odbiorcą. Nadmiarowa wartość zasila FP, brakująca FN, zgodna TP. Zapisz `2TP / (2TP + FP + FN)` globalnie, per klasa i per pole, obok liczby obserwacji i metodologii.
4. Testy evaluatora obejmują poprawny rekord, wartość błędną liczoną jako FP i FN, dokument bez wyniku, zbędny wynik dla negatywu, różną kolejność tych samych podmiotów, różnicę ról i powtórzenia. Uruchom tablicę bazową przed poprawkami. Najpierw usuń częste pomyłki z pierwszym zarzutem, podpisującym i pełnomocnikiem oraz rachunkami `z_rachunku` i `na_rachunek`. Porównuj kolejne wersje na tym samym modelu, konfiguracji i zestawie. Każdą zmianę uzasadnij przypadkami FP/FN.

**Odbiór.** Raport podaje źródło danych, podział spraw, commit, prompt i model, macierz klas, F1 z liczbą obserwacji, negatywy i błędy. Można go odtworzyć z tych samych plików bez wywołań dostawcy. Wyniki mają etykietę lokalnej ewaluacji. Oficjalny algorytm F1 pozostaje pytaniem U02. [Metodyka lokalna](../INTEGRATION_PLAN.md#lokalna-ewaluacja)

## BE05 · OCR na CPU

**Pliki.** Dodaj `src/kio_extract/ocr.py` i `tests/test_ocr.py`, w razie potrzeby zmień `pdf_reader.py` i inicjalizację procesora. Zależności renderera przypnij w `requirements.txt`. Tesseract i pakiet `pol` opisz w README i obrazie kontenera.

1. Zostaw pypdf jako pierwszą próbę odczytu tekstu. W `OCR(path, page_number)` renderuj tylko stronę wskazaną do OCR. Numer strony kontraktu jest od 1, a indeks renderera od 0. pypdfium2 i Tesseract to propozycja dla CPU. Renderuj pojedynczo z ograniczeniem czasu i rozmiaru obrazu, zwalniaj bitmapy i pliki tymczasowe. Przy obsłudze kilku żądań serializuj dostęp do PDFium w danym procesie, chyba że każdy render jest w odrębnym procesie. [Dokumentacja pypdfium2](https://pypdfium2.readthedocs.io/en/stable/python_api.html#incompatibility-with-threading) · [Dokumentacja Tesseract](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html)
2. W uruchomieniu sprawdź obecność silnika oraz `pol`. Tesseract wywołuj z listą argumentów i limitem czasu. Zwracaj tekst UTF-8 i zachowuj kolejność stron. Zostaw oryginalny tekst stron tekstowych. Sprawdź krótką stronę tekstową, skan i rzeczywiście pustą stronę osobno. Przy potwierdzonej pustej stronie zachowaj numer strony i pusty tekst. Przy nierozpoznanym skanie zwróć kod błędu zamiast zapisywać pozorny wynik. Dla brakującego silnika zachowaj `ocr_required`, a dla nieudanego wywołania użyj `ocr_failed` zgodnie z kontraktem.
3. W testach jednostkowych wstrzyknij atrapę renderera i OCR. Oddzielna próba integracyjna ma użyć prawdziwego silnika z polską próbą oraz sprawą mieszaną. Sprawdź, że czytelne strony ominęły OCR, skanowe trafiły do niego raz, a cały odzyskany PDF wysłał jedno żądanie LLM. Zweryfikuj timeout, brak binarki i sprzątanie plików.

**Odbiór.** Przetworzenie skanu i mieszanego PDF-u przechodzi na CPU przez ten sam procesor co zwykły PDF. Nierozpoznany skan daje błąd pojedynczego dokumentu, a pozostałe wyniki trwają dalej. Próba z prawdziwym OCR jest raportowana oddzielnie od testu z atrapą.

## BE06 · Uruchomienie, wydanie i demo

**Pliki.** Uzupełnij `README.md`, `requirements*.txt`, `Dockerfile`, `compose.yaml` i instrukcję wykorzystania API przez frontend. Dokumentacja wymienia tylko nazwy zmiennych i bezpieczne wartości przykładowe. Wyniki z PDF-ami oraz ewaluację trzymaj w katalogach roboczych.

1. Zapisz faktycznie sprawdzone polecenia dla instalacji Python 3.13+, standardowego CLI, CLI z LLM, API z atrapą i API z modelem docelowym. Przykładowy docelowy start API to `python -m uvicorn --app-dir src kio_extract.api:create_app --factory --host 127.0.0.1 --port 8000`. Dopasuj go do wdrożonej fabryki. W Compose wiąż port na hoście lokalnie i montuj `input/` oraz `output/` na potrzeby batcha. Przekaż klucz do procesu podczas uruchomienia. Sprawdź czystą instalację i podaj wymagania dotyczące OCR i języka polskiego.
2. Wspólnie przejdź przez jedną rzeczywistą sprawę w profilu spełniającym warunki konkursu. Zacznij od świeżego `output/`. Porównaj nazwy i schemat wyników z panelu i CLI. Sprawdź kolejność, negatyw i awarię jednego pliku. Jeśli kwalifikowany endpoint jest nadal niedostępny, przeprowadź demo syntetyczne i nazwij pozostały warunek próby rzeczywistej.
3. Na końcu wykonaj `python -m pytest -q`, próbę CLI, próbę HTTP, próbę OCR i końcową ewaluację na odłożonych przypadkach. Podaj uruchomione komendy, wyniki, ścieżki raportów, model, wersję prompta, ograniczenia oraz wymagane ustawienia na maszynie jury. W zgłoszeniu podaj udokumentowaną konfigurację z otwartym modelem i endpointem spełniającym warunki UZP albo odnotowane potwierdzenie odstępstwa.

## Raport po każdym zadaniu

Zapisz **COMPLETED**, **TESTS**, **OUTPUT**, **RISKS**, **BLOCKERS** i **NEXT**. Raportuj rzeczywiście uruchomione próby. Testy z atrapą nie potwierdzają jakości modelu ani działania natywnego OCR. Oznacz BE02–BE06 jako ukończone dopiero po przejściu ich kryteriów odbioru. Gdy docelowe API jest niedostępne, kontynuuj procesor, HTTP, testy deterministyczne, evaluator i OCR zgodnie z harmonogramem.
